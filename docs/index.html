Requirements, and why each one is there

A requirement without a reason cannot be pushed back on. The "why" column is what the requirement protects; the "challenge" column is the question that would remove it or change its shape. Several were reshaped by the component discussions below.

ID
Requirement
Why it's here
Challenge, and outcome
F1

One-to-one chat

Two users exchange text in real time.

Why

The base case every other flow degrades to.

Challenge

Is 1:1 just a group of two? Yes: one conversation table, one path.

F2

Group chat, up to 100 members

One message, many recipients, each with several devices.

Why

Forces the fan-out decision: 100 members × 1.5 devices is 150 deliveries.

Challenge

Why 100? Answered: it is the product today; 10 k+ communities are a Discord-style product with its own design pass.

F3

Real-time delivery

p50 under 100 ms, p99 under 500 ms, measured server to server.

Why

Sets the protocol: anything with request overhead per message fails the p50.

Challenge

Measured from where? Answered: chat-server ingress to recipient-socket write. The whole budget is inside our infrastructure.

F4

Offline delivery, notify, mark unread

Messages to an offline user wait and arrive on reconnect; every new message pushes a notification and marks the conversation unread.

Why

Separates "delivered to a server" from "delivered to a person".

Challenge

How long do we hold them? Answered: the fast path covers 24 h; beyond that the device loads from persistent history.

F5

Persistent history, kept forever

Any device can page back through the conversation.

Why

The write-heavy, read-recent access pattern is what picks the database.

Challenge

Server-side or device-only? Answered: server-side, forever; retention is a tiering question.

F6

Multi-device sync

Up to 5 devices per user share one conversation state.

Why

Turns "deliver to user" into "deliver to each device cursor".

Challenge

Do read receipts sync across the reader's own devices? Yes: one read cursor per user, not per device.

F7

Online indicator, must have

For the people on screen. Detected within 10 s, visible within 15 s, 5 s debounce.

Why

The most expensive cheap-looking feature; the cost is in propagation, not detection.

Challenge

To whom? Answered: only to who is looking (subscription), never to a whole contact list.

F8

Message status, per member

Sent, delivered, read. In groups the sender sees who read.

Why

Each transition is an event flowing backwards.

Challenge

Per member is 100 events per message if stored per message. Answered: one read cursor per member per conversation.

F9

Media up to 10 MB, server never processes it

No server-side pipeline; the client compresses images by default.

Why

Blob bytes dwarf text bytes and must never ride the real-time path.

Challenge

Was "full size" about fidelity or simplicity? Answered: simplicity, so client compression is in.

F10

Quoted reply

A message references one earlier message in the same conversation. Threads stay out.

Why

The first feature where a message depends on another message.

Challenge

Copy the quote or fetch by ID? Fetch by ID, placeholder if the parent is gone.

F11

Auto-reconnect

A client reconnects by itself when the network returns and resumes with no gap and no duplicates.

Why

Mobile radios drop constantly; without this "real-time" is only true on Wi-Fi.

Challenge

Designed in the transport component: jittered backoff, device cursor, client message ID.

Component 1

Transport, heartbeat, reconnect

How 15 million devices hold a connection, how the server notices one has silently died, and how a device gets back without losing or duplicating anything.

The problem

Three jobs hide in "keep-alive": keep idle sockets open through NATs and carriers; detect an unclean drop so presence can mark the user offline; let the client notice a half-open socket. A clean close is seen instantly by both sides. The heartbeat exists only for the unclean case, and the F7 target of 10 seconds sets its interval.

Decision

WebSocket for the real-time path; HTTPS for login, history paging and media.

Server-initiated ping frames every 5 s; two missed pongs mark the connection dead (≈ 10 s). Client mirror rule: no ping for 15 s, close and reconnect.

Reconnect with backoff 1 s → 30 s cap, ±30 % jitter; the hello frame carries the device cursor so the server replays what was missed before live traffic. Outgoing messages sit in a local outbox with a client-generated ID; the server dedups for 24 h.

Heartbeats never write to Redis. Pongs update a timestamp in memory; a sweeper closes stale sockets every second.

Detection timeline

The interval is set by F7's 10 s target: detection = interval × misses. Each halving of the interval doubles ping frames, which is cheap; what would not be cheap is a Redis write per pong, which is why there is none.

PingDetectionFrames/s per 100 k-socket server

Rejected

Client-sent JSON pingCode on every platform; competes with application backpressure; browsers already answer protocol pings for free.
TCP keepalive onlyKernel default is 2 h; invisible to the app on most mobile stacks; does nothing for the client-side half-open case.
Presence key refreshed per pong2 M Redis writes/s fleet-wide to answer a question the chat server already knows locally.
Long polling, SSE, MQTTRequest per message, one-directional, or a heavier client story on web. MQTT's "you'll rebuild half of it" point was accepted: the half is ping/pong, a cursor and a dedup key, about 200 lines per platform.
How we argued it

The canonical-design frame closed WebSocket immediately. Truc then asked for the heartbeat to be designed so it keeps the connection, reconnects, and knows which one is disconnected. The one real trade named: the 5 s interval exists only because F7 says 10 s; relaxing F7 would cut ping traffic three times. That turned out not to matter once the presence component showed detection is local and ping frames are the only cost.

ChallengeWebSocket gives nothing for free: no delivery guarantee, no resumption. Why not start from MQTT?
AnswerTrue, and the design is that missing half, explicitly. The ubiquity of WebSocket on web, and zero client code for protocol pings, outweigh it.

Full write-up: design.md §1.

Component 2

Message store, IDs, history

Where two billion messages a day go, how each one gets an ID that sorts and pages, and how a device shows the newest 50 and scrolls back through years without ever loading it all.

The problem

Append-heavy, read-recent, almost never update, 115 k writes/s at peak and 730 TB over five years. A store with a single writer is the ceiling; a partition that grows forever is the classic failure. And a cursor for paging must be unambiguous while new messages arrive.

Decision

Wide-column store (Cassandra or ScyllaDB), partition key (conversation_id, month bucket), clustering by message_id descending.

Snowflake IDs minted on the chat server: time plus node plus sequence in 64 bits, so the ID is both the sort key and the pagination cursor, and its timestamp selects the month bucket without a lookup.

History is kept forever server-side. Opening a conversation loads the newest 50; scrolling up pages older ones with ?before={message_id} over HTTPS, never over the socket.

Rejected

Postgres, shardedReads are fine; the write path funnels through one primary per shard and 730 TB of growth is manual sharding work. Parked under the canonical frame, with "nobody here has run Cassandra in anger" noted as the real risk.
Sort by created_atSame-millisecond collisions need a tiebreaker anyway, and a timestamp is an ambiguous cursor. Kept as a display column.
One partition per conversationUnbounded growth: a five-year-old group becomes one multi-GB partition.
Offset paging, full history on open, history over the socket, device-only historyO(n) and unstable; p50 impossible; competes with live delivery; fails new-device and lost-phone cases.

Layout and the two cursors

The five questions on Cassandra versus Postgres

Fast write and read?Commit log plus memtable, no B-tree, no primary: writes scale with nodes. Reads of "newest 50" are fast on both; the write path and the growth differ.
Transactions?One row per insert. Fan-out is deliberately not atomic; it is retried idempotently because the ID is fixed. Cross-row ACID is given up because nothing needs it.
CAP and ACID?AP with quorum writes at RF 3: a partition degrades to "delayed", never "cannot send". Duplicates are the price, handled by the client message ID. Atomicity and durability per row; isolation within a partition.
Why not created_at?Needs a tiebreaker anyway; ambiguous as a cursor. Snowflake is timestamp plus tiebreaker in one integer. Clock skew is accepted: a quoted reply carries its parent ID explicitly.
Sticky sessions?Sticky by connection, by nature of TCP. What is needed is the inverse lookup, user → server, in Redis. Never pin a user to a server across reconnects.
How we argued it

Truc asked the five questions above after the canonical frame put Cassandra on the board; the answers are the real argument. The storage-bound finding from estimation (2.2 PB on disk needs ~550 nodes for disk, ~15 for throughput) moved compression and tiering from optional to required. "Keep history forever" and "load newest, page on scroll" were product answers that fixed the partition and cursor design. Full write-up: design.md §2.

Component 3

Fan-out and queueing

Everything between "the chat server has stored the message" and "it is on every recipient's screen". Two decisions hide here: who does the delivery work and when, and whether a queue sits between the store and the screen.

The problem

A message to a 100-member group is 150 deliveries across up to 150 different chat servers. The average is far smaller, about 6, but the design must survive both. If every delivery passes through a durable queue, the queue's latency is paid on every message; if none does, an offline or slow recipient has nowhere to wait.

Decision

Fan-out on write. The sender's chat server does the work at send time: store, ack, then look up each recipient device's server and push.

Direct push for online recipients, server to server, no queue in the hot path.

A per-device sync queue for everything else: offline devices, reconnecting devices, and "did I miss anything". Backed by Redis Streams, one stream per device, IDs only, 24-hour window.

Write order is an invariant: message store, then sender ack, then queue append. Nothing is ever in Redis that is not already in Cassandra, so losing Redis loses no message, only the map of what each device still lacks.

Backpressure: a bounded per-destination buffer; if a recipient server does not take the push within budget, the message stays in that device's stream and the device catches up on its own. A slow recipient is a delay for one recipient, not a stall for the sender.

Hot path and catch-up path

Solid teal is the hot path, paid on every message inside the server-to-server latency budget. Dashed amber is the catch-up path, paid only by devices that were not there.

What the sync queue is, exactly

Not a work queue with competing consumers, and not a shared event stream. One append-only log per device of message IDs that device has not acknowledged, read by that device only. Three operations and nothing else: XADD on fan-out, XRANGE from the cursor on replay, XTRIM by time. Entries are ~50 bytes; bodies are joined from the message store on replay. Acking advances the device's cursor; nothing is deleted on ack.

Rejected

Kafka in the hot pathIts p99 alone can eat most of the 500 ms budget for a recipient who is online and could have been pushed to directly.
Cassandra table with TTL as the queue12 billion expiring rows a day is the tombstone failure mode; survivable only with daily partitions dropped whole, a lot of care for a one-day fast path.
Kafka, partition per user, as the queueWrite rate is trivial for it, but 15 million per-device consumers at arbitrary offsets is not its model, and it cannot hold our cursors.
30-day window54 TB live to serve the small fraction of reconnects that the slow path already handles correctly.
Queue rows with bodies; one queue per user; delete on ack40× the bytes and stale on edit; cannot express "phone behind, laptop current"; tombstones where the cursor already hides acked rows.
Fan-out on readRight for 100 k-member channels, the follow-up product; wrong for groups of 100 where recipients expect delivery without asking.
How we argued it

The canonical frame moved the lean from "Kafka-backed sync queue in the delivery path" to the textbook split: direct push for online, queue for catch-up. The remaining counterpoint, a slow recipient server stalling the sender, was answered with the bounded buffer and drop-to-stream rule.

Challenge: does the queue need to exist?After the store and cursor decisions, "what did this device miss" could be answered by comparing each conversation's newest ID with the device cursor and paging the store forward. The queue is a second write of every message per device, 12 billion appends a day, to save that comparison.
Truc's answer: keep it, and here is whyOn reconnect the chat list must show which conversations have new messages immediately, and open chats must then be complete. Those are two reads. Compare-and-page is right for the list and wrong for ordered replay across 200 conversations, which is exactly what the queue already is.
Challenge: the 30-day window was deciding the backing54 TB forces Cassandra or Kafka. What is the longest offline gap the fast path must serve?
Truc's answer: 24 hoursBeyond that, loading from persistent storage is accepted. At 1.8 TB live, Redis Streams fits and maps one-to-one onto the queue's three operations. And since the queue is not a core feature, losing Redis means loading more, never losing a message, which the write-order invariant guarantees.

Component 4

Reconnect, sync queue, cursors

What a device does in the first two seconds after it gets its network back, and who owns the three numbers that make "no gap, no duplicates" true.

The problem

A reconnecting device needs two different things, and no single structure serves both: the chat list, with unread dots and previews, right now; and every missed message, in order, so each open chat is complete. The first is a small bounded read; the second may be thousands of messages.

Decision

Chat list first, over HTTPS. One call returns a summary row per conversation that changed since the device's list cursor: last message ID, preview, sender, and an unread count derived by comparing the user's read cursor. Served from a per-conversation summary kept in Redis for conversations active in the last 30 days, from the store for the rest.

Then the socket and the replay. hello{cursor}; the chat server replays the device's stream from there in batches of 100, before live traffic. If the user opens a chat before its replay arrives, the client pages that conversation from the store and the replay dedups by ID.

Beyond 24 h the stream is trimmed past the cursor: summary first, then each chat loads from the store on open. Nothing is lost; the device pays latency.

Cursors: owner, durable copy, loss

CursorOwnerDurable copyIf lost
last_synced_message_id per devicethe device, sent in hellonone neededwiped device → new device → slow path. The server never stores it, so there is no second copy to disagree.

The one rule: losing a cursor must make the system replay more, never less. Over-replay is harmless because the client dedups by message ID. A cursor advances only after the device acks, never when the server has merely sent. Kafka is not a cursor store: its offsets name positions in Kafka, not message IDs in our store.

The cursor questions ("should cursors live in Redis or Kafka, and what if they are lost?") produced the ownership table and the replay-more-never-less rule. Component 5

Receipts, unread, notifications

Sent, delivered, read per member in a 100-person group; a conversation marked unread on every device until opened on one; and a push that wakes a phone without leaking the message.

The problem

Per-member read tracking is the expensive choice if done naïvely: 100 read events per message in a full group, each fanned out to 150 devices, is 15 000 receipt frames for one message and 100 receipt rows for every message row.

Decision

Reading is monotonic, so the state is not "who read message N" but "how far has each member read": one last_read_id per member per conversation, updated with max(), idempotent and order-independent.

Status is derived, never stored. Read if every other member's cursor is ≥ the ID; delivered if every device cursor is; else sent.

Receipts coalesced to one per conversation per 2 s, pushed only to members with that conversation on screen.

Unread is derived: newest message ID in the conversation > the user's read cursor. One cursor per user, not per device, so reading on the phone clears the laptop's badge.

Notifications go only to devices without a live socket, to all of them, carrying a hint and never the body. Mute and do-not-disturb are checked first.

Rejected

Receipt row per message per member100× the message write volume in groups; unbounded partition per message.
Push every receipt to every member15 000 frames per message; nobody looks at receipts for chats they are not in.
Per-device read cursorRead on the phone, still unread on the laptop; breaks F6.
Push with message bodyBody leaves our boundary; stale on delete or edit.
Stored unread counterHot key per user under fan-out; drifts from the cursor on any retry.

How we argued it

Truc chose per-member tracking and notify-and-mark-unread as requirements. The pushback was the 15 000-frames number; the answer was the monotonic cursor, which keeps the requirement and removes the cost. Full write-up: design.md §3.

Component 6

Presence

Online, offline, last seen: how fast a change is detected, who gets told, and why the number that made it look expensive was a coupling mistake.

The problem

Detection looked expensive because an early estimate tied a Redis lease, renewed every 30 s for 15 million sockets, to the 10 s target: 500 k writes/s. But detection is local to the chat server, and the lease exists only for a dead server, which service discovery already handles. The real cost of presence is propagation: a user with 200 contacts and 50 online produces 50 pushes per transition, and mobile radios transition constantly.

Decision

Subscription model. A device receives presence only for users on its screen: the open chat, the visible rows of the list. Leaving the screen unsubscribes.

Detected within 10 s; visible to watchers within 15 s normally, 30 s worst case. A drop-and-reconnect under 5 s is never shown as offline.

Lease decoupled from detection: renewed every 2 min with a 5 min TTL, a safety net behind service discovery's mark-all-offline on node loss.

Cross-server fan-out through a pub/sub channel per watched user, joined only by servers that currently have a watcher.

Rejected

Push every transition to all online contactsThe large number, for a contact screen the product does not have.
Pull on open onlyThe dot never changes while a chat is open.
Relax F7 to 30 sWould have saved nothing once the lease was decoupled; the heartbeat was never the cost.
No debounceEvery tunnel flaps the dot for all watchers and doubles pub/sub traffic.

State machine per user

How we argued it

Opened as "10 seconds or 30 seconds?". The first move was the correction above. Truc then answered the propagation question: only who is looking, and propagation need not be instant as long as the error is bounded. The bounds became numbers. Full write-up: design.md §5. Component 7

Media

The largest system on the page by two orders of magnitude, and the one where a single clarification of the requirement did more than any architecture choice.

The problem

At a 2 MB average, 10 % of two billion messages is 400 TB a day, a thousand times the text, with download bandwidth around 23 GB/s. That average came from one line in the spec: full size, no server-side resizing or transcoding.

Decision

"Full size" protects simplicity, not fidelity. There is no server-side media pipeline because that is a system of its own. The server never touches media bytes.

Compression is the client's job. Images compressed on the device by default (≤ 500 KB); the sender may choose "send original". The 10 MB cap is enforced by the pre-signed upload URL's content-length condition.

Bytes go client ↔ object storage directly. The message is sent only after the upload completes and references the object key.

Regional buckets; CDN only in front of group media. A 1:1 attachment is fetched 1.5 times, where a CDN adds a hop; a group attachment is fetched up to 150 times in a burst, the pattern a CDN exists for.

Authorization at URL-minting time against conversation membership; download URLs are 1 h bearer tokens.

Rejected

Originals by defaultFour times the dominant cost for fidelity nobody asked for in a chat.
Upload through the API serversEvery byte crosses our fleet twice to enforce a cap the signed URL already enforces.
Server-side thumbnails or transcodingA pipeline of its own; out of scope by F9. Clients render their own thumbnails.
CDN for everything; proxy downloads for authorization; global bucketA hop and a miss on every 1:1 download; bytes back through our servers; cross-region writes for intra-region chats.

Component 8

Runtime and prototype

What the chat servers run on, and why that question was only worth answering once we knew a prototype would exist.

The problem

Every other decision shows up in an artifact: the store shapes the schema, the transport shapes the heartbeat, the ID shapes the cursor. The runtime shapes none of those; Kotlin on Netty, Elixir and Go all hold 100 k sockets per node. So the first question was whether the decision was load-bearing at all.

Decision

There will be a prototype, and its job is to prove the heartbeat, reconnect and replay protocol, not connection count.

Node.js with TypeScript and ws for the prototype, because that is the fastest path: protocol-level ping/pong exposed directly, one file runs in minutes, and the load-balancer repo already uses the same tooling.

Production runtime: deliberately undecided. Kotlin on Netty remains the default for real work. BEAM is the language this problem was shaped by, and a Node prototype teaches nothing about connections per node; both true, both outside the prototype's stated goal. If that question becomes real, it gets its own prototype.

What the prototype proves

Built under prototype/: one Node.js process, in-memory ports, a scripted multi-device client. Six scripted scenarios run over the real server, on fake time with the design's numbers and (S1, S5) on real timers; all pass. What the build changed in the design is in What the prototype changed.

  1. S1 An unclean drop is detected by the server within 10 s and by the client on its own within 15 s; the reconnect carries the cursor and flushes the outbox with the same client message ID.
  2. S2 Reconnect with a cursor replays exactly the missed messages, in order, with no duplicates, before live traffic; a cursor moved backwards re-delivers and the device dedups.
  3. S3 A duplicate send is deduplicated by client message ID: one row, one queue entry, one deliver.
  4. S4 The chat list renders from the summary before the replay finishes; a cold open during the replay reads the store.
  5. S5 Presence by subscription: watch is batched and answered, a drop shows offline at ≈ t+15 s with last_seen=t, a reconnect inside the 5 s debounce shows nothing, pongs never write the lease.
  6. S6 A media message carries the key and metadata only; no URL and no byte crosses a socket; an intent over 10 MB is refused before any byte moves.
How we argued it

Challenge: what will be different in this repository depending on the runtime? Truc: there will be a prototype; its goal is protocol correctness; the shortlist is Kotlin or Node.js; the criterion is speed. Node.js followed. ADR: .memory/decisions/2026-11-01-prototype-runtime-nodejs.md.

Still open, and follow-ups

Nothing here blocks the prototype. Each is a task of its own, with the component it would change.

  1. Production runtime. Component 8. Re-decide when there is a product; a second prototype in Kotlin or BEAM is the honest way to compare connection handling.
  2. Service discovery. Components 1 and 6 depend on it (least-loaded server, mark-all-offline on node loss). The book says ZooKeeper; today that reads as etcd, Consul, or the orchestrator.
  3. Batch end on replay, and delivered receipts. Component 4. Nothing marks where a replay batch ends (batch_end flag or replay_done frame), and the replay ack could replace §3.4's delivered receipt. From the prototype, design.md §7.3.
  4. Presence debounce versus the client's reconnect. Components 1 and 6. The 5 s debounce, the 15 s mirror rule and the first backoff were sized independently and a half-open drop shows a flap; the relation they should keep is in design.md §7.4.
  5. The 10 % media rate. Component 7. The remaining lever on the dominant cost; halving it halves media.
  6. Discord-style communities. Groups of 10 k+ change fan-out (on read), presence (a member list is a "who is online" screen), and the message store partitioning. A separate design pass, spec §8.3.
