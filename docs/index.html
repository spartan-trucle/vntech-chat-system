Requirements, and why each one is there

A requirement without a reason is a requirement you can't push back on. The "why" column is what the requirement is protecting; the "challenge" column is the question that would remove it or change its shape. If a challenge wins, the spec changes.

ID
Requirement
Why it's here
Challenge this
F1

One-to-one chat

Two users exchange text in real time.

Why

The base case every other flow degrades to. If this isn't fast and durable, nothing else matters.

Challenge

Is 1:1 just a group of two? If yes, do we design one path or two?

F2

Group chat, up to 100 members

One message, many recipients, each with several devices.

Why

Forces the fan-out decision. At 100 members × 1.5 devices one send becomes 150 deliveries.

Challenge

Why 100 and not 500 or 100 000? The ceiling decides whether fan-out-on-write survives.

F3

Real-time delivery

p50 under 100 ms, p99 under 500 ms, both parties online.

Why

Sets the protocol: anything with request overhead per message fails the p50.

Challenge

Measured from where to where? Device-to-device includes the mobile radio; we can't control that.

F4

Offline delivery

Messages to an offline user wait, then arrive on reconnect.

Why

Separates "delivered to a server" from "delivered to a person". Introduces the per-user inbox.

Challenge

How long do we hold them? A week offline with 100 active groups is a big inbox.

F5

Persistent history

Any device can page back through the conversation.

Why

The write-heavy, read-recent access pattern is what picks the database.

Challenge

Does history belong on the server at all? WhatsApp historically kept it on the device.

F6

Multi-device sync

Up to 5 devices per user share one conversation state.

Why

Turns "deliver to user" into "deliver to each device cursor". This is the subtle one.

Challenge

Do read receipts sync across the reader's own devices, or only to the sender?

F7

Online indicator, must have

Online, offline, or last seen. Visible to contacts within 10 seconds.

Why

Presence is the most expensive cheap-looking feature: 10 M heartbeats on a clock.

Challenge

Is 10 s a product number or a guess? Each halving roughly doubles heartbeat load.

F8

Message status

Sent, delivered, read.

Why

Each transition is an event flowing backwards. Three small messages for every real one.

Challenge

In a 100-person group, do we track read per member, or just "read by some"?

F9

Media up to 10 MB, full size

Images, video, files. No server-side resizing or transcoding. One per message.

Why

Blob bytes dwarf text bytes by orders of magnitude and must never ride the real-time path.

Challenge

Full size on mobile data to 100 recipients is up to 1 GB per send. Who pays for that?

F10

Quoted reply

A message references one earlier message in the same conversation. Threads stay out.

Why

Cheap to add, but it is the first feature where a message depends on another message.

Challenge

Copy the quoted text into the reply, or fetch by ID? Deleted parents decide this.

The two numbers that should change your mind about something: the peak write rate rules out any store that needs a single writer, and the media volume means the blob store is a bigger system than the chat store.

Choosing the stack, one layer at a time

Each layer gets the question it has to answer, the candidates, the criteria that actually discriminate, a lean, and the best argument against that lean. "Open" means we have not argued it yet. A layer only turns "decided" after the counterpoint has been answered in writing.

Real-time transport

decided

How do 10 M clients hold a connection and receive pushes without polling?

Criteria: bidirectional, works through corporate proxies and mobile carriers, reconnect cost, library maturity on iOS, Android and web.

WebSocketBidirectional, universal client support, one TCP connection per device. Needs explicit heartbeat and reconnect logic.
Long pollingWorks everywhere, but one HTTP request per message and per timeout; p50 target is hard to hit.
Server-sent events + HTTPPush only; sends go over separate requests. Simpler, but two paths to reason about.
MQTT / XMPPPurpose-built messaging protocols. Great fit, smaller talent pool, heavier client story on web.
Decision

WebSocket for the real-time path; plain HTTPS for login, history paging and media. Server-initiated ping every 5 s, two misses = dead (10 s, matching F7); client reconnects with jittered backoff and resumes from its device cursor. Heartbeats never touch Redis. Full write-up: design.md §1.

Counterpoint, answered

"You end up implementing half of MQTT yourself." True, and §1 is that half: ping/pong, resume cursor, client-side dedup key. It is about 200 lines per platform, and we keep the ubiquity of WebSocket on web.

Chat server runtime

open

What holds millions of idle connections cheaply and routes messages between them?

Criteria: memory per idle connection, scheduler behaviour under 100 k connections per node, what the team can operate at 3 a.m.

Kotlin on Netty (Ktor / Micronaut)The team's stack. Netty handles the connection count; the JVM wants tuning for memory per socket.
Elixir / Erlang (BEAM)The textbook answer. WhatsApp and Discord's gateway. Per-connection processes, built-in supervision. New language for the team.
GoGoroutine per connection, small memory footprint, simple deploys. No actor model; you build supervision yourself.
Node.jsFast to prototype, single-threaded event loop; needs a cluster per core and careful backpressure.
Lean

Kotlin, because operating a system you know beats a system that is theoretically better. Netty is proven at this connection count.

Strongest case against

This is practice, not production. If the point is to learn why chat systems look the way they do, BEAM is the language the problem was shaped by. Picking the familiar stack may be picking the lesson we skip.

Message store

decided

What absorbs 115 k writes per second and serves "last 50 messages in this conversation" and "everything since cursor X"?

Criteria: write throughput without a single primary, partition by conversation, range scan by message ID, 730 TB of growth, operational burden.

Cassandra / ScyllaDBPartition on conversation, cluster on message ID. Discord's path. Wide partitions and tombstones are the known traps.
PostgreSQL, partitioned + shardedFamiliar, transactional, excellent tooling. Sharding by conversation is manual work and the ceiling arrives at the primary.
DynamoDBSame data model as Cassandra, zero operations, pay per request. Cost at 2 B writes/day is a real line item.
HBaseFacebook Messenger's original choice. Strong ordering per row, heavier to run than the rest.
Decision

Wide-column, partition key (conversation, month bucket), clustering by message ID descending. All history kept for 5 years; open loads the newest 50, scroll-up pages by cursor over HTTPS, never over the socket. Two cursors per device: oldest-loaded (back) and last-synced (forward). Full write-up: design.md §2.

Counterpoint, parked

"Nobody has run Cassandra in anger" is a real risk, but the frame chosen is the canonical design, so the practice is to learn it. Revisit if the frame changes.

Message ID

decided

How does every message get an ID that is unique, sortable within a conversation, and mintable at 115 k/s with no coordinator?

Snowflake-style (time + node + sequence)64-bit, roughly time-ordered, generated locally. Clock skew between nodes is the risk.
Per-conversation sequencePerfect ordering within a chat. Needs a counter per conversation, which is a hot key for busy groups.
Database-assignedSimple, but ties ID minting to the store's write path and its availability.
Decision

Snowflake minted in the chat server; the timestamp inside the ID also selects the month bucket for pagination, so a scroll-up cursor needs no lookup.

Counterpoint, accepted

Two messages in the same millisecond from different servers may swap. A quoted reply carries its parent ID explicitly, so the chain is still correct even if display order flips.

Routing, presence and session state

open

When a message arrives for Khanh, which server holds Khanh's three connections, and is Khanh online right now?

Criteria: sub-millisecond lookups, TTL-based expiry for heartbeats, pub/sub for presence fan-out, survives a node loss without a thundering reconnect.

Redis (cluster)Session map with TTL, presence with TTL, pub/sub for fan-out. One system, well understood. Not a durable store.
etcd / ZooKeeperRight for server discovery, wrong for 10 M user sessions churning every few seconds.
In-memory on the chat server + gossipNo external dependency, but every server must know every other's users. Does not scale past a few nodes.
Lean

Redis for user-to-server routing and presence with heartbeat TTL; etcd or the orchestrator for chat-server discovery only.

Strongest case against

10 M presence writes every heartbeat interval is a Redis cluster of its own. Should presence be pulled on demand when a chat opens instead of pushed on every change?

Fan-out and queueing

open

Between "stored" and "on the recipient's screen", is there a queue, and who consumes it?

KafkaDurable, replayable, partition per user or per conversation. Adds latency and a large operational surface.
Redis Streams / pub-subFast and already in the stack. Durability is weaker; losing a node can lose in-flight deliveries.
Direct push + per-user sync queueThe textbook path: store, push straight to online recipients' servers, and append to each device's sync queue for cursor catch-up and offline delivery.
NATS JetStreamLighter than Kafka, durable streams, less ecosystem.
Lean

Direct push for online recipients, per-user sync queue for everything else. Kafka left the hot path once the canonical frame was chosen. What backs the sync queue is still open.

Strongest case against

Direct push means a 100-member group with a slow recipient server stalls the sender's chat server. Where is the backpressure boundary?

Media storage and delivery

open

Where do 400 TB a day of full-size blobs live, and how do 100 recipients fetch the same 10 MB file?

Object storage + CDN, pre-signed URLsClient uploads straight to the bucket, chat server never touches bytes. Short-lived signed URLs handle authorization.
Upload through the API serversCentral place to enforce the 10 MB limit and scan content. Every byte crosses your fleet twice.
Peer-to-peer / device relayZero server storage; falls apart the moment the sender goes offline.
Lean

Direct-to-bucket upload with a pre-signed URL that encodes the size cap; message is sent after upload completes and references the object key.

Strongest case against

With no transcoding, a CDN only helps if recipients fetch roughly the same time. For a 1:1 chat it is pure cost. Do we need a CDN at all, or just regional buckets?

Push notifications

decided

How does an offline phone learn there is something waiting?

APNs + FCM via a notification serviceThe only way onto the device when the app is closed. Carry a hint, never the message body.
Decision

There is no real alternative; the only questions are what the payload contains and how to avoid notifying five devices for one message.

Still worth arguing

Should the push carry the message text for the lock screen preview, given it leaves our infrastructure?

Questions to settle before the first diagram

Answer these in order. Each one closes at least one "open" layer above.

  1. Is this exercise optimising for learning the canonical design or for what we would actually run? Answered: canonical design (Alex Xu ch. 12). Closed transport, store, ID and the fan-out direction. Did not close the runtime: the book is language-agnostic, so BEAM vs Kotlin is still open.
  2. Where is latency measured? If it is server ingress to server egress, Kafka in the hot path is affordable. If it is device to device, it probably is not.
  3. What is the group-size roadmap? If 100 is forever, fan-out on write is fine. If 10 000 is a follow-up, design the threshold now.
  4. Is 10 seconds for presence a product promise or a placeholder? Each halving roughly doubles the heartbeat load on Redis.
  5. Do read receipts in groups need per-member tracking, or is "read by N" enough? Per-member is 100 status events per message.
  6. Does the server keep history forever, or is it a relay with device-side storage? This changes the whole storage section.
  7. For media: regional buckets or global CDN? Full-size delivery without variants makes the CDN case weaker than usual.
