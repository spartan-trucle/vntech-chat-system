## The decision, as it goes into the text

1. Frames: `deliver` gains boolean `replay` (true from the `XRANGE` loop, false for a
   live push); one new server frame `replay_done`, no payload. No `batch_end`, no
   `replay_start`.
2. Server: on `hello{cursor}` subscribe live, run `XRANGE (cursor + COUNT 100` back to
   back until empty, pushing `deliver{replay: true}`, then `replay_done`. Never wait for
   an ack; the bounded per-destination buffer is the only flow control. On a push
   dropped by the budget: stop queuing live frames for the connection, let the buffer
   drain, re-run the loop alone from the dropped entry until empty, `replay_done`, then
   resume live. A further drop extends the loop. The initial replay runs alongside
   live; a backpressure replay runs alone.
3. Client: `ack{up_to_stream_id}` on its own cadence with the highest stored
   `replay: true` `stream_id` (every 100 replay frames or 500 ms, author's numbers to
   confirm). Replay mode begins at `hello` and at the first `replay: true` frame after
   a `replay_done`, ends at `replay_done`. In replay mode live frames are stored but
   their `stream_id` is not applied; outside it is, as today. Render sorted by
   `message_id`.
4. Item 8 is decided separately but on this ack, not on push-to-socket.
5. Rejected: `batch_end`; ack as credit; a single `replay_done`; closing the socket on
   a drop; `replay_start`.

## Checks against existing text

- §4.4 "the replay waits for each batch's ack": foreseen (ack is not a credit).
- The board and tradeoffs 5.8.3 place the bounded buffer on the sending server per
  recipient server ("if a recipient server does not take the push"); the ADR's re-replay
  needs the drop to be seen by the server holding the device's socket. Which hop the
  budget guards is not stated by the ADR. Reported as a surprise; the text is written in
  the ADR's words ("a live push to this connection dropped by the backpressure budget").
