## The decision, as it goes into the text

1. Live first, then replay. On `hello{cursor}` the chat server subscribes the
   connection to live pushes before the `XRANGE` loop. No replay phase, no flip.
2. A message appended during the replay reaches the device twice; the client's store is
   keyed by `message_id`, so the second copy is a no-op. Frames are not in `message_id`
   order on the socket during the replay; the client renders from its store sorted by
   `message_id`, the order the message store clusters by and the history page returns.
3. Cursor rule: the device cursor advances on replay batch acks only until the
   end-of-replay marker (item 7, now required). A live frame before the marker is stored
   but its entry id is not applied. After it, live frames carry their entry id
   (`stream_id` on `deliver`) and advance the cursor as today.
4. `XADD … *`, `message_id` in the entry body, no serialisation per stream. A late
   append is replayed, not refused. Idempotent retry on the retry path only: tail read
   (`XREVRANGE sq:{device} + - COUNT 100`), skip if present, best effort; client dedup
   by `message_id` is the guarantee. The two-layer dedup of the store ADR is unchanged.
5. Rejected: one more `XRANGE` after the flip; server-side buffer during the replay;
   explicit Snowflake stream ids with per-stream serialisation; `SET NX` per entry.
